# 下議會議員資料庫與投票模型規格

## 1. 文件定位

本文件定義 30 位虛構下議會議員，以及建立個人化投票模型所需的資料結構、初始行為參數與歷史投票樣本。

- 所有人名與人物設定均為虛構，不對應現實政治人物。
- 本資料用於取代單純的「七種立場常數」，使每位議員都有可追蹤的身分、偏好與投票歷史。
- 本文件是資料與邏輯規格，不包含可執行程式碼。
- 下議會固定席次為 30 席；一般法案至少需要 16 票贊成才能通過。

## 2. 資料分層

### 2.1 議員主檔

議員主檔保存相對穩定的身分資料：

| 欄位 | 定義 | 規則 |
| --- | --- | --- |
| `member_id` | 議員唯一識別碼 | `LC-001` 至 `LC-030`，不得重複或回收 |
| 姓名 | 顯示名稱 | 本版本全部唯一 |
| 性別 | 人物性別 | 女性、男性、非二元 |
| 年齡 | 當屆起始年齡 | 每個遊戲年度統一增加 |
| 選區 | 政治責任區域 | 北、東、南、西、中央五區，各六席 |
| 黨團 | 議員主要政治聯盟 | 黨團不是投票結果的硬性鎖定條件 |
| 性格標籤 | 三個穩定人格描述 | 用於辯論反應、事件與對話生成 |

### 2.2 投票行為參數

每位議員具有三項主要關注點，權重總和必須等於 100%。另外使用四個 0 至 100 的行為參數：

| 參數 | 低值含義 | 高值含義 |
| --- | --- | --- |
| 民意敏感度 | 不容易被民調影響 | 強烈跟隨選區民意 |
| 說服阻力 | 容易因辯論改變立場 | 很難被說服 |
| 黨團紀律 | 經常獨立投票 | 通常跟隨黨團共識 |
| 風險容忍度 | 偏好保守、可預測方案 | 願意支持高風險或長期方案 |

### 2.3 投票歷史

投票歷史必須採追加式保存，不應直接覆蓋舊紀錄。每筆紀錄至少包含：

| 欄位 | 用途 |
| --- | --- |
| `vote_id` | 單筆投票唯一識別碼 |
| `member_id` | 對應議員 |
| `bill_id` | 對應法案與版本 |
| 表決日 | 遊戲內日期 |
| 表決階段 | 初審、辯論後複決或最終表決 |
| 選擇 | 贊成、反對、棄權、缺席 |
| 投票前分數 | 保存模型作出判斷前的支持分數 |
| 最主要理由 | 當次影響最大的關注點 |
| 民意快照 | 投票當日的選區支持度 |
| 預算快照 | 投票當日的城市財政狀態 |
| 黨團建議 | 贊成、反對或自由投票 |
| 是否改票 | 是否在辯論後改變選擇 |

## 7. 下議會投票模型

### 7.1 評分順序

每位議員對每項法案獨立計算支持分數，建議流程如下：

1. 以中立值 50 作為起點。
2. 將法案效果對照議員前三項關注點，依 50%、30%、20% 或個人表中指定的權重加減分。
3. 套用黨團對該法案類型的建議，但影響程度由黨團紀律決定。
4. 套用選區民意；民意敏感度越高，選區支持度的影響越大。
5. 套用城市即時情勢，包括資金、赤字、滿意度、失業率、環境、治安與交通壓力。
6. 將過往同類法案的投票一致性加入小幅修正，避免人物毫無原因地反覆改變立場。
7. 辯論後按照說服阻力、辯論品質與是否回應主要疑慮計算第二次分數。
8. 最後加入幅度極小且可重現的個人波動，避免完全固定結果。

### 7.2 表決區間

| 最終支持分數 | 投票選擇 |
| ---: | --- |
| 55 以上 | 贊成 |
| 45 以下 | 反對 |
| 46 至 54 | 棄權；若黨團紀律高於 75，可改採黨團建議 |

缺席不應由支持分數決定，而應由健康、事件、停職、行程衝突等獨立狀態決定。

### 7.3 通過條件

- 有效席次固定為 30 席時，至少需要 16 票贊成。
- 棄權與缺席都不計入贊成票，但不降低法定過半門檻。
- 若之後加入停職或席次空缺，應另行保存「法定席次」與「現任有效席次」，不可只用當日出席人數作為門檻。

### 7.4 辯論與改票

辯論不應直接隨機翻轉投票，而應針對議員最在意的問題提供回應：

| 主要疑慮 | 有效說服材料 |
| --- | --- |
| 預算 | 分期預算、支出上限、財源證明 |
| 民意 | 選區民調、公聽會結果、受益人口 |
| 投資報酬率 | 回收期、稅收增量、成本效益分析 |
| 執行可行性 | 時程、責任單位、人力與風險控制 |
| 環境 | 排放、綠地、生態與長期成本 |
| 社會福利 | 覆蓋率、弱勢受益、分配公平性 |
| 區域平衡 | 各選區資源分配與地方補償 |
| 公共安全 | 風險降低幅度、應變能力與事故預防 |

只有辯論材料直接回應前三關注點時才給予明顯加分。說服阻力高的議員需要兩項以上有效材料，才可能改票。

## 8. 動態狀態

下列資料不應直接寫死在議員主檔，應作為會隨遊戲事件變化的即時狀態：

| 狀態 | 建議範圍 | 影響 |
| --- | ---: | --- |
| 與市長關係 | -100 至 100 | 影響是否信任市長提供的資料 |
| 選區支持度 | 0 至 100 | 影響連任壓力與民意修正 |
| 黨團關係 | 0 至 100 | 影響接受黨團建議的程度 |
| 廉政風險 | 0 至 100 | 只由事件累積，不應隨機指控人物 |
| 疲勞 | 0 至 100 | 過高時增加缺席或棄權可能性 |
| 當期承諾 | 多筆清單 | 記錄市長協商時答應的政策條件 |
| 當期立場 | -100 至 100 | 顯示辯論前後對特定法案的支持程度 |

## 9. 資料一致性規則

1. `member_id`、姓名不得重複。
2. 每位議員必須恰好有三項主要關注點，權重合計為 100。
3. 所有行為參數必須介於 0 至 100。
4. 投票只能使用贊成、反對、棄權、缺席四種結果。
5. 投票歷史不得因重新載入或重新模擬而重複寫入。
6. 每筆投票必須保存法案版本，避免法案內容修改後仍被誤認為同一份提案。
7. 個別議員可以違反黨團建議，但必須能由個人關注點、民意或事件狀態解釋。
8. 玩家可見的投票理由應取自實際最高影響因素，不應只顯示隨機台詞。

## 10. 與現有專案的整合界線

- 現有 `COUNCILORS` 七種立場可保留作為舊版相容資料，但不再作為正式議員名單。
- 現有七個下議院 profile 應被 30 位議員個人資料取代；原本的立場 bias 可以轉化為黨團或關注點修正。
- 現有八項法案可直接使用本文件 B01 至 B08 的歷史樣本作為模型校準資料。
- NPC 資料庫需要新增議員身分關聯時，應以 `member_id` 連結 NPC，而不是複製姓名與人格資料，避免兩份資料不同步。
- 議員主檔、動態狀態、投票歷史應分開保存；存檔時三者都需要版本號。

## 11. 驗收標準

- 能列出全部 30 位議員及個人資料。
- 同一法案能產生 30 筆可解釋的獨立投票。
- 辯論前後的改票可以追溯到明確原因。
- 重新讀取相同存檔後，投票結果與歷史紀錄保持一致。
- 黨團傾向會影響結果，但不會讓所有同黨議員永遠投相同票。
- 城市財政、民意與選區狀態改變時，最敏感的議員會率先改變立場。
- 玩家介面能顯示議員姓名、三項關注點、當前立場及過去投票。
