# 城諾之音：遊玩效能與功耗驗證計畫

狀態：`PLANNED`。本文件定義量測與驗收方式；目前沒有宣稱效能或功耗已改善，也不授權在缺少 profile 時降低 NPC 數量、動畫品質、天氣效果或畫面解析度。

## 目標

1. 讓一般遊玩、興建、交通規劃與市政視窗維持穩定幀時間。
2. 暫停或隱藏的 UI、天氣、交通與教學元件不應持續做不必要的每幀工作。
3. 所有最佳化都必須以同一裝置、同一解析度、同一場景的前後證據決定，不以主觀感覺或平均 FPS 取代尾延遲。
4. 不以犧牲 NPC 可見數量、腳影著地、避障正確性、即時資料或操作回饋換取通過。

## 現況與證據缺口

- 現有 `population_200k_capacity_benchmark` 驗證模擬容量，不代表實際渲染、UI、NPC 與天氣同時運作時的幀時間。
- 專案尚無原生視窗的遊玩 frame-time p50／p95／p99、卡頓比例、記憶體與 CPU／GPU 忙碌度證據。
- 靜態檢查發現數個「待量測候選」，不是已確認瓶頸：
  - `scripts/app/main.gd::_process()` 每幀呼叫 `_layout_map_stage()`。
  - 天氣與交通車輛控制器保留 `_process()`，即使當下沒有需要呈現的活動。
  - 教學背景在可見時持續漂移動畫；隱藏時已有早退，但仍需量測排程成本。

## P0：先建立可重跑的原生量測器

新增獨立 runner 與 deterministic fixture，輸出 append-only JSON；每次執行必須記錄：

- Git HEAD、tree、受測來源 fingerprint、Godot 執行檔 SHA-256。
- Windows 版本、CPU、GPU、驅動、螢幕更新率、電源模式與解析度。
- warm-up 30 秒、正式採樣 120 秒；原生視窗，不使用 headless 或 SubViewport 代表遊玩結果。
- 每幀 delta 的 p50、p95、p99、最大值，以及超過 25／33.3／50 毫秒的幀數與比例。
- Godot 靜態／動態記憶體、程序 working set、程序 CPU time；能可靠取得時再記錄 GPU busy。
- 若系統沒有可校正的硬體功率感測器，只能將 CPU time、GPU busy 與喚醒頻率標為「功耗代理指標」，不得宣稱瓦數或電池續航。

runner 必須隔離 `APPDATA`／`LOCALAPPDATA`、拒絕覆寫既有輸出、保留失敗原始日誌，並在來源於執行期間變動時 fail closed。

## P1：固定四個遊玩情境

| 情境 | 固定內容 | 目的 |
| --- | --- | --- |
| A. 暫停閒置 | 24 名 NPC、晴天、無視窗、遊戲暫停 | 找每幀空轉與基本功耗代理 |
| B. 城市運作 | 24 名 NPC 移動、建築施工、時間前進 | 量 NPC、導航、施工與 HUD |
| C. 高視覺負載 | 雨天、24 名 NPC、營運中交通車輛 | 量天氣、NPC 與交通疊加 |
| D. 管理操作 | 連續開啟城市數據、建築藍圖、交通規劃並修改選項 | 量 UI 重建、即時估價與圖表動畫 |

每個情境至少執行三次，報告中同時保留每次結果與中位數，不刪除離群失敗。

## P2：驗收門檻

門檻分成「體驗底線」與「相對回歸」；兩者都必須通過。

### 1920×1080、60 Hz 目標裝置

- p95 frame time ≤ 16.7 ms。
- p99 frame time ≤ 25 ms。
- 超過 33.3 ms 的幀 < 0.5%。
- 120 秒內不得有超過 100 ms 的非載入幀。

### 2880×1800 高解析度驗證

- p95 frame time ≤ 33.3 ms。
- p99 frame time ≤ 50 ms。
- 超過 50 ms 的幀 < 1%。
- UI 字體、按鈕、NPC、腳影與天氣品質不得為了門檻而降級。

### 相對回歸與資源

- 相同情境相對核准基線：p95、p99、CPU time／wall time 及 GPU busy 不得惡化超過 10%。
- 120 秒採樣後 working set 不得持續單向成長；三次執行的結束值差異不得顯示累積洩漏。
- 暫停閒置情境的 CPU time／wall time 必須顯著低於城市運作情境；若無法降低至少 30%，視為需分析的空轉警訊，而不是直接判定產品失敗。

## P3：只對已證實熱點動手

優先順序如下，每項各自形成可回滾提交並重新跑四情境：

1. 若 `_layout_map_stage()` 佔用明顯，改由 viewport／比例／節點尺寸變更時重新排版，保留初始與 resize 行為。
2. 若隱藏或空集合控制器仍有成本，依可見性與是否存在車輛／效果切換 `set_process()`。
3. 若 NPC 導航是熱點，先快取不變的可走圖與路徑查詢；不得取消避障、允許穿越地形或減少 24 名可見 NPC。
4. 若天氣繪製是熱點，優先批次化或降低無效重建；不得刪除雨勢回饋。
5. 若 UI 重建是熱點，縮小 refresh 範圍並維持玩家每次選擇後立即更新估價與資料。

## P4：每批完成條件

- 聚焦測試與完整 74 項 assertion matrix 通過。
- `save-qa` 通過，確認最佳化未破壞存檔與權威狀態。
- 原生 `ui-qa` 通過，包含教學對話條與主要 UI 的真實視窗截圖。
- 四情境前後對照報告綁定 exact HEAD／tree；未通過時保留失敗證據並回滾該批。
- 最終由獨立唯讀審查者檢查量測方法、契約與畫質／功能回歸。

## 執行決策

本輪只交付量測規格與靜態候選清單。下一個最低足夠路由是 T2-H：先實作 P0 runner，取得基線後才決定是否進入 P3；在基線產生前，任何效能或功耗改善聲明都標記為 `UNVERIFIED`。
