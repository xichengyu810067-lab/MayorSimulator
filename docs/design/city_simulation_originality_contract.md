# Mayor Simulator 原創城市模擬設計契約

狀態：Goal #8 的設計基線，供後續實作、內容製作與驗收使用
適用範圍：城市空間、交通、公共服務、治理、人口／NPC、經濟、存檔與其玩家可見因果
不取代：既有程式、catalog、平衡數值、UI／美術規格及測試 manifest

## 1. 契約目的與原創性邊界

Mayor Simulator 可參考成熟城市模擬遊戲共有的高層問題，例如土地限制、路網連通、運輸營運、公共服務取捨與財政回饋；不可複製任何特定作品的專有名稱、分類組合、圖像、圖標、UI、版面、提示文案、教學順序、數值、地圖、音效、視覺語言或逐項系統配置。

本專案的設計來源優先順序如下：

1. Mayor Simulator 的 Goal #1–#9 與使用者後續澄清。
2. 本專案現有的權威 state、catalog、system、service、save schema 與測試契約。
3. 現實世界的城市治理、基礎設施與公共政策概念。
4. 同類作品僅作抽象層級的深度標竿，不作內容或介面範本。

每項新增設計必須能以「Mayor Simulator 的市長治理角色、居民訴求、權力制衡或可追溯市政因果」解釋其必要性。若一項提案只能以「另一款遊戲也有」辯護，則不納入本契約。

## 2. 既有權威基線

本契約承認下列已存在且不得被設計文件虛構覆蓋的能力：

- 城市狀態已有財政帳本、時間、建築、施工、NPC、事件簿、治理與維護資料。
- 地形可標記樹木、山丘／峭壁、河流／湖泊等阻擋；整地後才解除地形阻擋。
- 建築 catalog 已涵蓋住宅、商業、產業、休閒、教育、醫療、安全、交通、公共事業與行政設施。
- 交通權威模型已有道路、捷運軌道、鐵路、跑道、滑行道，並有機廠、號誌、車站、平交道、施工、拆除、維護、路線、票價、班距、車隊、啟停、連通驗證與持久化。
- 新遊戲不預埋可營運交通；站點或裝飾本身不得生成車輛或收入。
- 有效路線才能生成車輛、提供服務與收入；必要拓撲被拆除後，路線停擺且車輛、服務、收入歸零。
- NPC 有個體資料、就業、收入交易、關係、政策態度、居民請求與事件紀錄；地形、建築、施工與交通設施可成為導航阻擋。
- 治理已有行政提案、議會審議、司法與監察、強制施行的制衡紀錄，以及不滿／信任造成的終局失敗。

尚未由上述基線證明的深層能力，例如逐戶土地權屬、完整貨物流、逐車塞車、管線水力、逐建築服務半徑或土地價值市場，不得在 UI 或宣傳中假裝已存在；只能列為後續模組。

## 3. 核心玩家循環

核心循環以「觀察—承諾—建設—營運—問責—修正」為一個可持久化週期：

1. **觀察**：查看地形、既有土地使用、交通連通、財政、公共服務、居民請求與治理案件，辨識可說明的問題。
2. **承諾**：選擇回應居民、提出政策／法案或設定一項建設及營運目標；承諾必須留下狀態與責任紀錄。
3. **建設**：選址、整地、鋪設連續道路／軌道／跑滑道、建站與必要設施；支出與工期在完成前即構成限制。
4. **營運**：配置路線、車隊、班距、票價、維護與公共服務預算。只有物理條件及制度條件均成立，產出才生效。
5. **問責**：時間推進後，帳本、服務可達性、人口／就業、居民態度、請求狀態、議會與監督機關反映結果。
6. **修正**：玩家可調整、停駛、拆除、改線、增建、撤回或承擔失敗；修正不可抹除已發生的歷史與成本。

最小可玩閉環必須同時存在：一個空間決策、一個營運決策、一個居民或治理回饋，以及一筆可追溯的財政結果。單純放置建築後立即增加抽象分數，不足以構成 Goal #8 的完整閉環。

## 4. 跨系統因果鏈

### 4.1 土地與地形

**玩家輸入**：選取地塊、檢視地形限制、整地、保留自然地貌或選擇替代路徑。
**權威狀態**：地形種類、是否平坦、整地施工、占用者、導航阻擋。
**必要因果**：非平坦或受保護地形 → 禁止直接施工 → 玩家支付整地成本並等待工期 → 地形狀態完成變更 → 才可進入建築或交通施工。
**回饋**：明確顯示阻擋原因、預估成本／工期與完成後可用性；不得把自然地形偷偷改成道路或軌道。

土地模組的原創重點是「市長對地貌改造負責」：保留自然地貌應可能降低直接開發量，卻改善環境、居民信任或災害韌性；整地提高可建性，也留下成本及環境後果。第一階段可先以可建／不可建與整地狀態表達，不虛構精細地質模型。

### 4.2 道路

**玩家輸入**：選擇連續地塊建造或拆除道路，連接建築、站點與機廠。
**權威狀態**：道路 segment、連接方向、施工狀態、維護狀態、交叉設施與相鄰可達點。
**必要因果**：連續道路 + 合法端點 → 建築／站點取得道路可達性 → 私有車流或公車服務才可能成立；道路斷裂或維護失效 → 相關可達性下降或路線停擺。
**回饋**：區分「已鋪設」「連通但未服務」「有效營運」「斷線／停擺」，不得用車輛動畫假裝連通。

第一階段不要求逐車微觀交通 AI；可用可重現的拓撲容量、需求與服務係數計算壓力。但任何抽象值都必須由實際路網和城市活動推導，不能由無關動畫或固定背景產生。

### 4.3 軌道與平交道

**玩家輸入**：鋪設捷運或鐵路軌道、設置相容車站、機廠、號誌和平交道。
**權威狀態**：軌道種類、連續路徑、必要設施、交叉點安全狀態、路線有效性。
**必要因果**：相容站點 + 連續軌道 + 必要機廠／號誌／平交道 → 路線可啟用 → 列車依權威路徑運行；缺少任一必要條件 → 明確拒絕或停擺。
**回饋**：列車接近時的平交道動作必須對應真實路線與位置；純循環裝飾不算驗收。

### 4.4 公共運輸

**玩家輸入**：建立站點順序、選擇模式、車隊、班距、票價、啟用／停駛／刪除路線。
**權威狀態**：路線 ID、模式、站點、權威路徑、營運狀態、失效理由、需求、收入與成本。
**必要因果**：土地使用與人口產生出行需求 → 有效網路及營運配置供給服務 → 可達性、候車負擔與票價共同決定使用 → 影響收入、交通壓力、居民態度與就業可及性。
**回饋**：玩家必須能追溯「哪一條線、哪個條件、哪筆成本／收入」造成變化。拆除或斷線時，該線車輛、服務與收入同時歸零。

公車、捷運、火車與航空可有不同必要設施和成本結構，但共享同一套原創生命週期語言：規劃、施工、驗證、營運、停駛、斷線、修復、拆除。不得照搬他作的路線顏色規則、資訊面板或模式解鎖順序。

### 4.5 公共服務與公共事業

**玩家輸入**：選址建造教育、醫療、安全、消防、公園、水、能源、燃氣、垃圾等設施，設定費率或預算。
**權威狀態**：設施容量、道路／運輸可達性、維護、費率、需求與服務結果。
**必要因果**：設施存在只是供給前提；設施完成 + 可達 + 有維護資金 + 容量可用 → 服務才改善居民結果。高費率、容量不足、斷路或欠維護 → 服務下降、遷移壓力或居民請求增加。
**回饋**：把「設施效果」拆成供給、可達、負荷與結果四層；初期尚未實作容量時，UI 必須誠實標示使用簡化係數。

### 4.6 治理與財政

**玩家輸入**：編列建設／維護預算、設定服務費與運輸營運、提出法案、回應居民、選擇是否強制施行。
**權威狀態**：帳本、承諾、法案狀態、議員投票、司法／監察案件、信任、不滿與失敗鎖定。
**必要因果**：空間問題或居民需求 → 行政選擇 → 財政與立法約束 → 執行結果 → 議會、司法、監察和居民反應 → 信任／不滿與後續權限改變。
**回饋**：每項重大政策至少顯示提案者、狀態、主要理由、預估與實際成本、受影響指標及制衡紀錄。強制施行可加速決策，但必須留下可被司法和監察檢查的風險。

### 4.7 NPC 與居民因果

**玩家輸入**：不直接操控 NPC；透過城市、服務、交通、費率、政策與個案回應影響居民。
**權威狀態**：個體身份、住居／工作關聯、就業、收入、政策態度、關係、請求、事件與可行走路徑。
**必要因果**：土地使用及職缺 → 居民／工作分布 → 路網與運輸決定可達性 → 就業與服務結果影響收入、態度及請求 → 玩家回應再改變城市與治理。
**回饋**：個體卡片只顯示權威資料；NPC 必須避開樹木、水體、峭坡、建築、施工、道路、軌道與交通設施等不適行走區域。導航失敗應停留或改道，不得穿越障礙來維持動畫。

居民請求狀態必須持久化且可追溯：待處理 → 已受理或已拒絕；已受理者在權威條件成立後 → 已完成。拒絕、受理與完成均保留歷史，不因 UI 重開而消失。

### 4.8 一條完整示例鏈

居民反映就醫不便 → 玩家受理請求 → 選址受地形阻擋 → 玩家整地並等待完工 → 興建醫院及連接道路／公車 → 服務在設施、連通、維護和容量均有效後提升 → 居民可達性改善、請求完成 → 維護與運輸成本進帳本 → 滿意／信任變化進入治理上下文。鏈中任一必要連接被拆除，服務結果必須下降，且完成過的歷史仍保留。

## 5. Mayor Simulator 原創差異化支柱

### 支柱 A：可問責的市長承諾

建設不是匿名工具操作，而是可被居民、議會、司法和監察回看的行政承諾。預估、決定、完工、營運與結果形成同一條稽核鏈。

### 支柱 B：權力制衡是城市系統，不是事件裝飾

行政效率與民主／法治風險同時存在。法案、強制施行、議員投票、司法停令、監察調查與終局失敗，必須能實際改變可做的城市決策或其成本，而非只提供背景文字。

### 支柱 C：居民是具歷史的個體證人

宏觀指標必須能向下連結到具名 NPC 的工作、收入、態度、請求與事件；NPC 不是只為畫面熱鬧而生成。為效能可只顯示代理人，但代理資料必須源自權威人口狀態。

### 支柱 D：先證明因果，再增加規模

每個可見產出都要有權威來源：車輛來自有效路線，服務來自可達設施，收入與成本來自帳本，請求完成來自真實條件。寧可使用較少模式與較小地圖，也不以裝飾模擬未存在的系統。

### 支柱 E：童話城市外觀下的嚴謹公共責任

視覺可保持 Mayor Simulator 自有的童話／繪本方向，但資訊層必須清楚區分事實、預估、警告與政治主張。畫風不可遮蔽路網斷線、施工阻擋、治理風險或財政後果。

## 6. Goal #1–#9 對應

| Goal | 本契約中的設計責任 | 最小可驗收結果 |
| --- | --- | --- |
| #1 民情狀態 | 居民請求是持久化承諾與歷史 | 拒絕、受理、完成顯示正確狀態；完成需權威條件成立 |
| #2 交通圖標／設施 | 可見交通物件只代表真實設施、路線與運行 | 各模式設施、導引路徑與車輛可辨識；零有效路線即零營運車輛 |
| #3 地圖格與縮放 | 所有空間權威狀態使用同一 tile／座標映射 | 縮放後建築、NPC、地形、交通、阻擋與點選仍對齊 |
| #4 音效／配樂 | 模擬事件可觸發音訊，但設定層獨立控制 | 音效與配樂音量分離、持久化，且靜音不改變模擬結果 |
| #5 NPC 避障 | 導航從完整的權威阻擋集合重建 | NPC 不穿越地形、建築、施工、道路、軌道與設施；變更後可重算 |
| #6 動畫 | 動畫是權威狀態的投影 | 施工、車輛、平交道等動畫與真實狀態同步，停擺即停止相應動態 |
| #7 整地 | 非平坦地形是建造前置條件 | 未整地不可建；整地有成本、工期、狀態與存檔結果 |
| #8 城市模擬深度 | 建立空間—營運—居民—治理—財政閉環 | 至少一條跨系統因果鏈可正向成立、破壞後反向失效、修復後恢復 |
| #9 SDK／skills | 契約轉為 canonical tests 與 fresh evidence | 新驗收加入 manifest，以全新輸出目錄執行，不沿用舊綠燈 |

## 7. 非目標

- 不重製、相容或模仿 Cities: Skylines 1／2，也不承諾功能一對一對等。
- 不採用他作的品牌用語、DLC 分類、道路／分區名稱集合、圖標、色碼、版面或教學流程。
- 不以逐車、逐戶、逐管線的全微觀模擬作為首個里程碑；可先使用可重現、可解釋的聚合模型。
- 不在本契約指定平衡常數、解鎖表、地圖尺寸、UI 像素或美術資產。
- 不把背景動畫、裝飾車流、固定粒子或隨機 NPC 當成模擬證據。
- 不保證現有 catalog 的每項建築已具有完整容量、覆蓋或物流模型。
- 不藉 Goal #8 重寫既有治理、司法、監察、存檔或 SDK 架構；擴充必須走明確介面。
- 不在未有測試前宣稱災害、貨運、土地市場、區域經濟、能源潮流或複雜交通號誌已完成。

## 8. 可測 Acceptance Criteria

以下 AC 使用穩定語意而非指定 UI 版面或平衡數值；實作時每項須對應 automated test ID，涉及畫面者另有可見驗收。

### AC-01 新局零權威交通

- 新遊戲的交通 segment、facility、route 與 active line 為空。
- 只有站點、背景道路或動畫時，營運車輛、服務係數和交通收入均為零。

### AC-02 地形前置條件

- 對樹木、山丘／峭壁、河流／湖泊等不可建地直接發起建築或交通施工時，操作被拒絕並返回穩定原因碼。
- 完成整地前不可占用；完成後阻擋更新，且成本、工期與結果可存檔還原。

### AC-03 道路與軌道拓撲

- 玩家選取的合法連續路徑完成施工後，權威 segment 保留完整 tile path。
- 非連續、種類不相容、端點非法或與未整地地形衝突的路徑不得成立，也不得扣除重複費用。

### AC-04 運輸完整生命週期

- 每個模式至少有一個 fixture 驗證必要站點、連續導引路徑及必要設施。
- 缺任一條件時建立／啟用失敗並提供可定位原因；條件完成後才可營運。
- 停駛、刪除或破壞拓撲後，active line、車輛、服務與收入同步更新。

### AC-05 成本與收入可追溯

- 施工、拆除、設施、segment、車站與車隊成本各自可追溯，且外部已計費的車站維護不得重複計費。
- 只有營運路線產生服務收入；相同 seed、輸入與狀態得到相同結果。

### AC-06 公共服務不是放置即生效

- 至少以醫療、教育或安全中的一類證明：設施存在、可達、維護與需求／容量條件共同決定服務結果。
- 斷路、停運或欠維護會降低結果；修復後可依相同規則恢復。

### AC-07 居民請求閉環

- 待處理請求可進入已受理或已拒絕，兩者均保留於公共事務歷史。
- 已受理請求只有在其權威城市條件成立後才能成為已完成。
- 狀態變更觸發事件與存檔，載入後狀態及完成條件語意一致。

### AC-08 NPC 導航一致性

- 所有權威地形、建築、施工與交通阻擋均同步到同一導航快照。
- 新建、拆除、整地或路網變更後，舊阻擋不殘留、無關阻擋不遺失。
- 可見 NPC 不穿越任何不可行走中心或多邊形；找不到路時不直線穿透。

### AC-09 治理與問責

- 一項城市政策能留下行政提案、議會結果與帳本／指標效果。
- 強制施行必須留下制衡紀錄，並可開啟司法及監察流程。
- 不滿或信任達失敗條件後，終局事件只發出一次，受保護的後續操作被鎖定，存檔後仍一致。

### AC-10 正向、破壞、修復三段驗收

- 建立一條至少橫跨地形／建設、運輸或服務、居民、財政的完整鏈，記錄基線與正向結果。
- 拆除或停用一個必要節點後，下游效果依規則失效，不得保留幽靈車輛、收入、服務或完成條件。
- 修復必要節點後，系統重新驗證並恢復合法效果；歷史成本與事件不被抹除。

### AC-11 存檔與決定性

- 土地／地形、施工、交通、服務、居民請求、治理與帳本的新增權威欄位均有版本化存檔契約。
- 存讀前後拓撲、狀態、失效理由與經濟語意一致；相同 seed 與命令序列產生相同摘要。

### AC-12 UI 與動畫誠實性

- UI 明確區分規劃中、施工中、完成、營運、停駛、斷線及拆除，不以顏色作唯一線索。
- 圖標、動畫、車輛數與平交道動作都來自權威 snapshot。
- 不載入或關閉動畫時，模擬結果不變。

### AC-13 縮放與空間對齊

- 最小、預設、最大縮放下，tile 命中、建築、NPC、地形、交通路徑、車輛與導航阻擋使用一致的座標轉換。
- 同一測試點在縮放前後解析到同一權威 tile／物件。

### AC-14 Fresh evidence

- 新增測試須進入 canonical assertion manifest；禁止用單次手工截圖替代邏輯測試。
- 以 SDK 在全新輸出目錄執行 focused test、完整 verify、UI QA 與涉及存檔時的 save QA。
- 任一非零退出、缺少成功標記、解析錯誤、資源洩漏或殘留 owned process 均不算通過；舊證據不代表新工作樹。

## 9. 後續模組邊界

| 模組 | 擁有的權威資料／責任 | 只可透過介面取得的外部資料 | 不得直接負責 |
| --- | --- | --- | --- |
| Terrain / Land | 地形種類、坡度級別、整地、可建性、自然阻擋 | 建設占用、政策保護狀態 | 財政扣款、車輛生成 |
| Construction | 工程報價、占用、工期、完成／拆除命令 | 地形許可、帳本授權、catalog spec | 直接改居民態度或畫動畫 |
| Transport Network | segment、facility、station、crossing、route、拓撲驗證 | 地形可建性、建築站點、人口需求 | 擁有地形、直接繪圖 |
| Transport Operations | 車隊、班距、票價、狀態、服務與營運摘要 | Network 有效路徑、人口／土地需求 | 修改拓撲或 NPC 真實資料 |
| Public Services | 供給、可達、容量／簡化負荷、服務結果 | 建築、路網、人口、維護 | 直接制定法律或生成建筑 |
| Population / NPC | 個體、就業、收入、態度、請求、事件 | 城市服務、可達性、政策結果 | 決定建設合法性、扣市庫 |
| Governance | 法案、投票、司法、監察、信任、不滿、權限 | 財政與城市效果摘要 | 修改 tile、偽造居民事件 |
| Economy / Ledger | 每筆收入支出、餘額、原因與 subject ID | 各系統經授權的交易命令 | 推斷地形或 UI 狀態 |
| Save / Event | schema、原子持久化、事件序列、遷移 | 各模組的版本化 snapshot | 發明缺失的 runtime 狀態 |
| Presentation | 座標投影、UI、圖標、動畫、音訊 | 唯讀權威 snapshot／view model | 成為模擬真相或反向偷改狀態 |

跨模組寫入應使用命令／事件或明確 service API；禁止 UI、動畫 controller 或 catalog 在讀取時產生副作用。新增欄位要指定單一擁有者、序列化位置、穩定 reason／error code 與至少一個契約測試。

## 10. 避免抄襲檢核表

任何設計、UI、內容或素材進入實作前，作者與審核者各自檢查一次：

- [ ] 問題與機制是否可由現實城市治理或 Mayor Simulator 既有因果說明，而非只引用某款遊戲？
- [ ] 名稱、文案與分類是否由本專案自行命名，沒有照搬專有用語或相同組合？
- [ ] 操作流程、頁面資訊架構、面板位置、圖標、色碼與視覺階層是否為獨立設計？
- [ ] 數值是否來自本專案平衡目標與測試，而非抄錄、近似換算或微調他作數值？
- [ ] 地圖、道路配置、建築外型、角色、截圖、音效與宣傳文案是否未臨摹或重製他作資產？
- [ ] 若使用現實資料，是否記錄來源、授權／使用條件與轉化方法？
- [ ] 若使用生成式工具，是否保存 prompt／provenance，且 prompt 未要求重現特定作品的畫面或 UI？
- [ ] 提案是否至少强化一項 Mayor Simulator 原創支柱？
- [ ] 可見效果是否能追溯到本專案權威狀態，而非為了看起來像另一款遊戲？
- [ ] 實作 PR／變更說明是否列出獨立設計理由、資料擁有者、驗收項目與來源記錄？

任一項無法確認時，先隔離提案，不得進入 runtime catalog 或發行素材。相似性爭議由專案負責人裁決；裁決前採保守方案：重新命名、重畫、重排流程、重新平衡，或移除該項。

## 11. 變更與驗收治理

- 本契約描述目標語意，不授權直接改動程式、catalog、UI 或平衡值。
- 後續模組可分階段實作，但每階段必須標出「權威模擬」「簡化估算」「純顯示」三者之一。
- 新增深度時優先完成一條跨系統閉環，再擴增更多建築或交通模式。
- 若現有實作與本契約衝突，以現有行為作基線、建立明確遷移計畫與回歸測試，不得靜默改變存檔語意。
- Goal #8 只有在 AC-01 至 AC-14 各有可定位證據，且至少一條完整因果鏈通過正向、破壞、修復與存讀驗收後，才能宣稱完成。
